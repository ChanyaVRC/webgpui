# WebUI GPU Engine 要件定義（Rust）

## 1. 目的
Rust で GPU レンダリング可能な WebUI エンジンを開発する。

- 高速描画（GPU活用）
- クロスプラットフォーム対応（まずは Linux / Windows）
- 将来的な拡張性（UIコンポーネント、アニメーション、テキスト、入力）

## 2. スコープ
### 2.1 MVP（最初のリリース）
- ウィンドウ生成
- GPU コンテキスト初期化
- 基本図形描画（矩形、線）
- 色・透明度の指定
- リサイズ対応
- 入力イベント取得（マウス、キーボード）
- 最小限の UI ノードツリー（レイアウトは簡易）

### 2.2 将来拡張（MVP外）
- 高機能レイアウト（Flex/Grid互換）
- テキストレンダリング最適化
- 画像、SVG、フィルタ
- アニメーション・トランジション
- アクセシビリティ対応
- 開発者ツール（インスペクタ、プロファイラ）

## 3. 前提技術
- 言語: Rust（stable）
- GPU API 抽象化: wgpu
- ウィンドウ/イベント: winit
- 数学: glam（必要時）
- シリアライズ: serde（必要時）

## 4. 機能要件
### 4.1 レンダリング
- 毎フレームの描画ループを提供する
- 描画コマンドをバッチ化できる構造を持つ
- DPI スケーリングに対応する
- VSync の有効/無効を設定可能にする
- パイプライン切り替え回数を最小化するソート戦略を持つ
- インスタンシング描画を利用できる設計にする
- 静的ジオメトリは再アップロードせず再利用できる
- 部分再描画（dirty rect）に対応できる描画境界を管理する

### 4.2 UI ツリー
- ノードの追加/削除/更新ができる
- 親子関係を保持する
- 変更時に再描画範囲を特定できる設計にする（将来最適化）

### 4.3 イベント処理
- マウス移動、クリック、スクロールを取得できる
- キーボード入力を取得できる
- フォーカス管理の基本動作を持つ

### 4.4 API 設計
- アプリ側から宣言的に UI を組み立てられる API を提供する
- 内部実装を隠蔽し、公開 API は安定性を優先する
- エラーは Result ベースで返却し、原因を追跡可能にする

### 4.5 既存エンジン互換・移行
- 既存 WebUI エンジンの主要概念（Node, Style, Event）に対応する互換レイヤーを提供する
- 既存 API を直接置換しやすい Adapter API（Facade）を提供する
- CSS 互換を目指し、MVPでは頻出プロパティ（position, size, margin, padding, background, border, opacity）を優先対応する
- 既存イベントモデル（capture/bubble相当）の基本動作を提供する
- 段階移行を可能にするため、新旧エンジンを同一アプリ内で共存可能にする（画面単位またはコンポーネント単位）
- 移行ガイドと API マッピング表を提供する

## 5. 非機能要件
### 5.1 パフォーマンス
- 目標フレームレート: 60 FPS（標準環境）
- UI 更新がない場合は無駄な再描画を抑制する
- 起動時間を短くする（初期目標: 1秒未満）
- フレーム時間目標: 平均 16.6ms 以下、p95 20ms 以下
- CPU メインスレッド予算: 1フレームあたり 4ms 以下（MVP目標）
- GPU 描画予算: 1フレームあたり 8ms 以下（MVP目標）
- ドローコール目標: 主要画面で 200 以下（MVP目標）
- メモリアロケーション目標: フレーム中のヒープ確保を原則 0 に近づける

### 5.2 信頼性
- GPU 初期化失敗時に分かりやすいエラーを出す
- パニックを最小化し、回復可能な失敗はハンドリングする

### 5.3 保守性
- モジュール分割（renderer, scene, input, platform）
- 単体テスト可能な責務分離
- 公開 API のドキュメント整備

### 5.4 互換性・運用性
- 公開 API の互換性ポリシー（semver）を定義する
- 既存エンジンからの移行コストを定量管理する（書き換え行数、差し替え箇所数）
- 後方互換を壊す変更には migration note を必須化する

## 6. アーキテクチャ方針
- `platform`: ウィンドウ、イベント、OS依存処理
- `renderer`: wgpu 初期化、パイプライン、描画実行
- `scene`: UIノード管理、差分更新
- `input`: 入力状態とイベント配信
- `app`: 利用者向け API 層

## 7. 開発マイルストーン
1. プロジェクト初期化（Cargo workspace、基本モジュール）
2. ウィンドウ + wgpu 初期化
3. クリアカラー描画
4. 基本図形描画
5. イベント入力処理
6. 簡易 UI ツリー連携
7. サンプルアプリ作成
8. 最低限のテスト/計測

## 8. 受け入れ条件（MVP）
- 主要環境で起動し、ウィンドウ表示できる
- 60 FPS で基本図形を描画できる
- リサイズ時に表示が崩れない
- 入力イベントがアプリ層で取得できる
- サンプルで UI ノード更新が描画に反映される
- 代表的な既存UI画面を 1 つ以上、互換レイヤー経由で再現できる
- 既存実装からの移行サンプル（Before/After）を 1 つ以上提供する

## 9. リスクと対策
- GPU/ドライバ差異: バックエンド選択とフォールバック方針を準備
- API の肥大化: MVP は最小公開 API に限定
- 最適化の早期着手: まず機能完成、次に計測ベースで最適化

## 10. 次アクション
- プロジェクト構成（crate 分割）を決める
- MVP の API スケッチを作る
- 最小サンプル（ウィンドウ + クリア描画）を実装開始

## 12. 代替可能性の判定基準
- API 代替率: 対象既存エンジンの主要 API の 80% 以上をカバーする
- 画面再現率: 対象 UI の 90% 以上を視覚的に再現する
- 速度要件: 同一画面で既存比 1.2 倍以上の平均 FPS または同等 FPS で CPU/GPU 使用率を削減する
- 移行コスト: 既存画面 1 つを 2 人日以内で移植可能である

## 11. レンダリング高速化方針（優先順）
1. 計測基盤の先行実装
- CPU: フレームごとの更新時間/描画時間を分離して計測
- GPU: timestamp query によるパス単位計測

2. バッチング最適化
- 同一パイプライン、同一テクスチャ単位でコマンドを集約
- インスタンシング可能な図形はまとめて送信

3. データ転送最適化
- 永続利用バッファを使い、map/unmap 頻度を抑制
- 動的更新領域は ring buffer で管理してコピー回数を減らす

4. 再描画最適化
- UI 差分から dirty rect を生成し、変更領域のみ再描画
- 更新がない場合は描画をスキップし、入力時のみ再描画するモードを提供

5. パイプライン最適化
- 頻出パイプラインを初期化時に作成
- シェーダ分岐を減らし、頂点フォーマットの種類を最小化

6. 並列化
- UI 更新（CPU）と GPU 送信準備を分離し、将来的にワーカースレッド化
